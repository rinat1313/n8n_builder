# Конвейер: ТЗ → n8n-конфигурация

Полный цикл сборки проекта для n8n. Ведёт **planner**. Пока фаза не завершена — не перескакивать дальше.

Справочник ролей: [references/roles.md](references/roles.md).  
Фазы и артефакты: [references/phases.md](references/phases.md).

## 0. Приём ТЗ

1. Получить ТЗ от пользователя.
2. Определить имя проекта:
   - есть в ТЗ → нормализовать в slug;
   - нет → придумать подходящее короткое имя по функционалу.
3. Вызвать `ensure_project`, сохранить исходное ТЗ в `projects/<проект>/tz.md`.
4. Загрузить skill `project-folders` при сомнениях по хранилищу.
5. Передать управление planner (делегировать subagent `planner`).

## 1. Сбор данных и вопросы (цикл уточнения)

Planner:

1. Смотрит `projects/<проект>/` — есть ли уже данные по проекту.
2. Собирает контекст (`get_project_context`) и передаёт специалистам:
   `architect`, `programmer`, `analyst`, `n8n-specialist`, `sql-programmer`.
3. Специалисты анализируют и готовят **вопросы пользователю**.
4. Planner **задаёт вопросы пользователю** и **останавливается**.
   Пока ответов нет — дальше не идти.
5. После ответов сохранить их в `projects/<проект>/answers/` и снова прогнать специалистов.
6. Повторять цикл, пока у специалистов не закончатся вопросы.

## 2. Разработка решений (без вопросов пользователю)

1. Planner отдаёт ТЗ + ответы специалистам.
2. Специалисты готовят решения (архитектура, алгоритмы, реализуемость, n8n-схема, данные).
3. Вопросы пользователю на этой фазе **запрещены**.
4. Результаты — в `projects/<проект>/solutions/`.

## 3. Пул задач и исполнение

1. Planner на основе решений создаёт пул задач в `projects/<проект>/tasks/`.
2. Делегирует исполнителю (`executor`) задачи на готовые n8n-конфигурации.
3. Исполнитель пишет экспорты; черновики в `projects/<проект>/drafts/`, финал после тестов — в `configs/<проект>/`.

## 4. Тестирование

1. Конфигурацию передать `tester`.
2. Тестировщик только анализирует и проверяет, **правки в код/конфиг не вносит**.
3. При провале — замечания в `projects/<проект>/tests/`, planner возвращает на доработку исполнителю.
4. При успехе — зафиксировать отчёт о прохождении.

## 5. Документация

1. После успешных тестов делегировать `technical-writer`.
2. Писатель оформляет описание в `description/<проект>/` доступным языком, при необходимости со схемами.

## 6. Итоговый отчёт planner

Planner пишет краткий отчёт в `projects/<проект>/report.md`:

- что сделано;
- что не сделано;
- где какие проблемы;
- рекомендации.

Показать отчёт пользователю.
